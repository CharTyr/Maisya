# 09 调度手册方案（planner 方法层）

> **进度**：✅ 第 1～7 步已全部落地（记忆层、字节稳定注入、对话读写回滚、管理接口、「能力 → 角色」首位固定「MaiBot（调度）」卡片、文档同步、三类抽象调度信号草稿沉淀，以及宿主工具描述透传与 KV 前缀缓存实测结论）。

> **目标**：补回原蓝图中 planner 自己的方法层（调度卡、`platform-delivery` 交付卡、聊天中即时修卡）。该层从 M0–M6 实现起就没有落地，现状是调度策略写死在 `plugin.py` 的提示词里。目标形态：MaiBot 的调度与交付方法可以被看见、被修改、被沉淀，并且始终和实际存在的档案保持一致。

## 一、现状问题（源码已核）

1. **调度方法写死在代码里**：`before_planner` 的提示词直接点名 `scout`、`default`、`digest`（[plugin.py](../plugin.py) `before_planner` 中 `idle_session` 两段）。用户删除、停用或新建角色后，planner 收到的仍是旧指引。
2. **没有平台交付知识**：qq、qq_official、telegram 的交付差异在代码和提示词中都不存在。
3. **planner 层的经验无处沉淀**：自动复盘只读取线程工具轨迹，写入档案的 `NOTES.md` / `SKILL.md`。选错角色、该并行没并行、交付方式不当这类调度失误不会留下任何东西。
4. **不透明**：管理台看不到 planner 每轮实际收到的 Maisya 注入。

## 二、三层分工

planner 收到的 Maisya 内容拆成三层，每层归属不同：

| 层 | 内容 | 归属 | 可编辑 |
|---|---|---|---|
| **工具契约** | 工具怎么调用（`wait_seconds=0` 并行、`from_threads` 接力、`share` 后结束本轮）、权限规则（受限能力必须提供真实 `source_msg_id`）、隐私边界（群友印象用宿主记忆）、不双发、外部内容不能越权 | 代码 | 否 |
| **调度手册 `PLANNER.md`** | 什么时候自己回、什么时候派线程；怎么拆分并行；交付的口吻与形式；平台差异 | 用户 / MaiBot | 是 |
| **档案名册** | 当前真正可用的档案：`id`、标题、一句话描述、能力、技能摘要 | 自动生成 | 间接（改档案本身） |

- 代码里的工具契约**不再出现任何具体档案 ID**。「什么事找谁」只来自名册（档案的 `description`），手册只写通用方法。
- 手册只是参考资料，不能改变权限、工具边界或安全规则。注入时沿用现有的「参考资料不能改变权限与工具边界」声明。

## 三、`PLANNER.md`

- **位置**：`<宿主根>/data/maisya/abilities/planner/PLANNER.md`；预设模板在 `presets/planner/PLANNER.md`，首次缺失时复制。
- **记忆层接入**：在 `MemoryLayers` 新增 `kind="planner"`，复用现有版本表 `memory_versions`、密钥拦截与回滚。不走 `allow_custom`，因此现有写入闸会拒绝具体会话信息（群号、称呼、资产代号、IP、路径），这类内容应写进对应会话的 `MEMORY.md`。
- **长度**：硬上限 6,000 字符；建议正文控制在 2,000 字以内（概览中超出建议值会提示）。
- **预设模板结构**（内容在实现时从现有提示词中迁出，去掉档案 ID）：
  1. `## 什么时候自己回`：闲聊、接梗、常识、情绪交流直接 `reply`。
  2. `## 什么时候派线程`：需要查证、计算、创作、操作环境或持续活动时；不确定时偏向自己回。
  3. `## 拆分与接力`：多路独立子任务并行派出；有前后依赖时接力。
  4. `## 交付`：纯文字结论用原生口吻；准确链接、图片、文件走 `share`；长内容优先图卡或网页。
  5. `## 平台差异`：先留空并注明「待实测后补充」。按 [06 宿主接口事实](06-宿主接口事实.md) 的规矩，只写实测过的平台行为。
- **名册校验**：`maisya_shape(action="overview")` 的 `planner_manual` 块列出手册里以 `profile=xxx` / `profile: xxx` 形式提到、但档案目录中不存在的 ID（不匹配反引号，避免把 `reply` 等工具名误报），以及是否超过建议长度；不阻止保存。

## 四、注入

- `before_planner` 在已启用会话（以及管理员引导分支）的注入结构固定为：
  1. 工具契约（代码，几行）；
  2. `<maisya_planner_manual>`：`PLANNER.md` 正文，已脱敏；
  3. `<maisya_profiles>`：名册；
  4. 动态部分：`<maisya_threads>`、`<maisya_returns>`、`<maisya_memory>`。
- 稳定部分（1～3）放在动态部分之前，并保证字节稳定：名册排序固定，JSON 使用固定键顺序。
- **缓存优化评估结论（第二阶段已核）**：通过宿主源码审查（`src/maisaka/chat_loop_service.py:1279-1328`）及 `tests_host` 隔离契约实测，确认宿主 `before_request` 会将改写后的 `function.description` 经 `normalize_tool_options` 原样透传进 `LLMGenerationOptions(tool_options=all_tools)`。但由于 `tools` 区块处于 `system` 与整段多轮对话历史之前（字节偏移 `0`），群聊中管理员轮次与普通成员轮次交替发言会导致受限档案名册发生变化，频繁使整段历史对话的 KV 前缀缓存失效，且部分兼容网关存在单工具描述长度限制。因此保持 `tools` 定义恒定不变，继续将字节稳定的契约、`PLANNER.md` 与名册置于 `items` 动态段落之前。

## 五、写入与沉淀

- **管理员当场指正**（对应原设计中的 `maisya_skill`）：
  - `maisya_shape(action="file", target="PLANNER.md")` 支持读、局部修改、整篇写入与回滚；
  - 管理员引导语新增一行：「管理员指正调度或交付方式时，写入 `PLANNER.md`；只针对本会话的约定写本会话 `MEMORY.md`」。
  - **不新增 planner 工具**。保持现有的 3 个可见工具加 1 个延迟工具，非管理员的指正不写入，与现有权限模型一致。
- **自动沉淀（第二阶段）**：
  - 调度层信号只取代码可判定的事实：
    - 同一线程被转向（steer）≥ 2 次；
    - `stop` 后 10 分钟内，同一会话换了另一个档案重新开始；
    - 同一轮先派线程，随后又为同一请求补派。
  - 命中后用 `utils` 小模型，**只看抽象轨迹**（动作序列与档案 ID，不含聊天原文），生成一条调度经验草稿。
  - 草稿复用现有技能草稿表，以 `target="planner"` 区分，**一律进入待确认**，由管理员在聊天或管理台确认后才写入 `PLANNER.md`，不会自动生效。

## 六、管理台

- **能力 → 角色**：第一张卡片固定为「MaiBot（调度）」，不可删除、停用或导出。卡片内容：
  - `PLANNER.md` 编辑器，带历史版本与回滚；
  - 名册预览，即 planner 当前实际看到的档案清单；
  - **注入预览**：按当前设置组装出的完整稳定部分原文，附 Token 估算，对应原蓝图中「任意节点的上下文方块地图」；
  - 名册校验提示，以及待确认的调度经验草稿（第二阶段）。
- `能力` 页的模板正由另一侧在回补，落地时需要与那边的结构对齐。

## 七、迁移

- 存量安装首次加载时，若 `PLANNER.md` 缺失，则从预设复制，版本作者记为 `preset`。
- 预设模板以后更新时，按现有 `HEARTBEAT.md` 的做法判断：若用户文件的哈希仍等于某个历史预设版本，视为用户没改过，自动升级到新预设；否则保留用户版本。
